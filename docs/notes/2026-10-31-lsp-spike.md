## 2026-10-31, Language server spike (#236)

JupyterLab's language server features (`jupyterlab-lsp`, and the `@jupyterlab/lsp` package it builds on) talk to `jupyter-lsp`, a Python server extension. This spike read `jupyter-lsp` 2.3.1 and captured its traffic with JupyterLab 4.6.5, `jupyterlab-lsp` 5.3.0, `typescript-language-server`, and `jedi-language-server`, to decide whether Ganymede should serve the same endpoints.

Recommendation: build it, as one small crate behind configuration. `jupyter-lsp` is a language-free relay once its Python spec finders are left out, so a Rust version keeps the host knowing no language.

### Endpoints

The frontend calls two endpoints and reads two page config keys. Nothing else.

- `GET /lsp/status` returns `{"version": 2, "sessions": {...}, "specs": {...}}`, both keyed by server name. A session is `{handler_count, status, last_handler_message_at, last_server_message_at, spec}`; status is one of `not_started`, `starting`, `started`, `stopping`, `stopped`. Specs are sent with `argv`, `debug_argv`, and `env` blanked (`[""]`, `[""]`, `{}`). The frontend picks a server by matching a document's language or MIME type against each spec's `languages` and `mime_types`.
- `WS /lsp/ws/{server}` relays JSON-RPC. Each websocket text frame is one JSON-RPC message with no `Content-Length` header; the server adds the header on the way to the language server's stdin and strips it from stdout. Auth is the same as the kernel websocket (cookie or token; `jupyter_server`'s resource name is `lsp`, action `execute`).
- Page config `rootUri` (`file://` URI of the contents root) and `virtualDocumentsUri` (`rootUri` + `/.virtual_documents`). The client uses them as the LSP `rootUri` and as the base for notebook documents. Ganymede's lab page config already sends `rootUri`; `virtualDocumentsUri` is missing.

The captured order for a plain `.ts` file: `GET /lsp/status`, websocket open, `initialize`, `initialized`, `workspace/didChangeConfiguration`, `textDocument/didOpen` with the real file URI (`file:///…/demo.ts`), then `didChange` (full text each time), `hover`, `documentHighlight`, `completion`, `completionItem/resolve`, and `publishDiagnostics` back. The server only relays; it reads none of it except for virtual documents.

### Server discovery

`jupyter-lsp` merges three sources: Python entry points (spec finders that look for `pyright`, `typescript-language-server` in `node_modules`, and so on), the traitlet `LanguageServerManager.language_servers` in `jupyter_server_config.*`, and `conf.d` JSON. Config wins; `autodetect = False` turns the finders off. The finders are the only part that knows languages.

For Ganymede, specs come only from configuration: a `[lsp.servers.<name>]` table in `ganymede.toml` with the same fields as `jupyter-lsp`'s spec (`argv`, `languages`, `mime_types`, `display_name`, `env`, `requires_documents_on_disk`, `workspace_configuration`). Reading `LanguageServerManager.language_servers` from an existing `jupyter_server_config.json` would be easy (it is plain JSON) and lets a Jupyter setup carry over, but can wait until someone asks. The spike ran `jupyter-lsp` with `autodetect: false` and a config-only spec for both servers, and the frontend behaved the same as with autodetect.

### Virtual documents

A notebook is sent to the language server as one document: the code cells of one language joined with blank lines, at `{virtualDocumentsUri}/{notebook path}` (captured: `file:///…/.virtual_documents/py.ipynb`). The client does all the joining and position mapping.

The server's part is the "shadow" file system: for `didOpen`, `didChange`, and `didSave` whose URI is under `virtualDocumentsUri`, and only for servers whose spec leaves `requires_documents_on_disk` true (the default), it writes the document's text to that path before relaying. It applies at most one `contentChanges` entry, the full text or a single range edit, and clears the directory on first use. Servers that read files from disk (`pyright`, `jedi` for imports) need this; the spike saw `.virtual_documents/py.ipynb` written with the joined cells. In Rust this is about 80 lines plus a check that the path stays inside the virtual documents directory, which `jupyter-lsp` also does.

### Process lifecycle

One process per configured server, shared by every websocket to it: started when the first websocket subscribes, terminated when the last one closes. Messages from the server are broadcast to every subscribed websocket, so two tabs see each other's replies, and the second tab's `initialize` goes to an already-initialized server. Ganymede should copy this for compatibility; a per-client process is a later option. stdio framing is `Content-Length: N\r\n\r\n` + body; `jupyter-lsp` ignores other headers and polls non-blocking pipes with backoff, which Tokio's async pipes make unnecessary. It does not restart a crashed server or log its stderr (stderr is inherited). `env` values expand `${VAR}` from the server's environment. Stopping is `terminate()` with no `shutdown`/`exit` request.

### Which frontends use it

- JupyterLab with `jupyterlab-lsp` installed. JupyterLab 4's core `@jupyterlab/lsp` only does something with an extension that uses it. Against Ganymede today (checked with the same JupyterLab and extension, `--static-dir` and `--labextensions-path` pointed at the venv), `/lsp/status` returns 404, the console logs the failed request, no websocket opens, and the notebook otherwise works.
- ganymede-ui has no LSP client. Its CodeMirror cells could use `@jupyterlab/lsp` or a CodeMirror LSP client over the same websocket; the Swift text editor (ganymede-ui #122) could too, against a remote server.
- For TypeScript notebooks on cdp-kernel, completion and hover already come from the kernel (`complete_request` and `inspect_request`, answered by a TypeScript language service worker that knows the executed cells). LSP adds diagnostics, go to definition, rename, and signature help, and covers plain `.ts` files in the file editor, which the kernel cannot.
- A TypeScript notebook on cdp-kernel did not attach in `jupyterlab-lsp` 5.3.0 under `jupyter-lsp` either: the websocket never opened, and the console showed "Cannot read properties of undefined (reading 'isReady')". The same setup worked for a `.ts` file and for a Python notebook. This is a client-side issue to look at before claiming TypeScript notebook support; it is not specific to Ganymede.

### iPad

No subprocesses on iOS, so the in-process server has no language servers there; the app would use LSP only through a remote Ganymede server. An on-device TypeScript service would run in the kernel web view, as cdp-kernel's language service does, not through `/lsp/*`.

### Security

The websocket path names a configured server; an unknown name is a 404 and never spawns anything, and no request can supply an `argv`. Shadow writes go only under the virtual documents directory inside the contents root. The status endpoint keeps `jupyter-lsp`'s blanking of `argv` and `env`.

### Lessons

- TypeScript 7 (the native port) ships no `tsserver.js`, so `typescript-language-server` fails `initialize` against it; the spike pinned `typescript@5`. A spec's `argv` points at whatever is installed, so this is the user's setup, not ours, but the docs should say it.
- JupyterLab restores the last workspace, so a capture script that opens a second document must use a fresh workspace (`/lab/workspaces/<new>/tree/…?reset`) or it reuses the first document's editor.
