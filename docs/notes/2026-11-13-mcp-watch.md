## 2026-11-13, `ganymede mcp watch` and the requests monitor (#785)

Part of #763, decision 2(a). `ganymede mcp watch` polls
`notebook_requests` (#783) on the server `mcp call` would find, and
prints a line per request once its text has stayed the same for
`--settle` seconds, once per text; answered requests drop out. It knows
no read mark and no session: Claude Code gives a plugin monitor no
session id, so the watch looks at requests, which live in the server's
rooms, not at a session's marks. The journal plugin declares it in
`monitors/monitors.json` with `when: on-skill-invoke:journal`, so it
runs only once a session has used the journal skill. Whether a monitor's
line starts a turn in an idle session isn't documented; the check is in
ganymede-ui#399.

From the review: each call has a 10-second timeout, so a server that
takes the call but doesn't answer is looked for again rather than
stopping the watch. The plugin installs from `main`, while `ganymede`
on `PATH` is usually the latest release, which has no `mcp watch`; the
monitor checks `mcp watch --help` first and exits 0 without it.
`notebook_requests` indents a cell's own lines that start `@@`, so they
can't pass for a request header, and a request missing from up to two
replies in a row (a notebook the server failed to read) isn't printed
again. Each poll still opens a new MCP session; reusing one is a
follow-up.
