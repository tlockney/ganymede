## 2026-11-13, a token only /mcp accepts (#766)

The security read of 2026-11-13 (#746, finding 3): `/mcp` sat behind the
API's auth, so an agent held the server's token, which also passes
every REST and websocket route. `mcp_read_only` and `mcp_no_execute`
limited the MCP tools only; the same agent could `PUT /api/contents`,
start kernels, open terminals or change grants directly.

`mcp_token` is a second token that `/mcp`'s own middleware
(`mcp::auth`) checks before falling through to `auth::api`. It passes
the request on without setting the login cookie that a token-authenticated
API request gets, since that cookie would open every other route.
Nothing else knows the token, so the rest of the API answers 403. The
server's token still works on `/mcp`, so `ganymede mcp`, which reads it
from the server info file, and the page are unchanged.

With auth off (`token = ""`) the key does nothing: every route is open
anyway. An empty `mcp_token` counts as unset, so it can't match an empty
`Authorization: token` header.

`the_mcp_token_reaches_only_mcp` checks `/mcp` with the token
(initialize, tools/list, a read-only refusal) and 403 with no cookie on
contents, kernels, grants, runs, terminals and a kernel websocket, by
header and by `?token=`.

After review: `mcp_token` confines an agent only while it can't run
code, since a cell can read the server's token from the server info
file or the config; docs/mcp.md, docs/security.md and the config doc
say so, and that an agent reads the server's token in any output that
shows it. Published pages, over MCP or from the browser
(`/nbconvert/html`), replace `mcp_token` as they do the server's token:
`server_redactions` reads it from `AppState.mcp`.
