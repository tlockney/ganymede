## 2026-11-09, JupyterLab 4.6.6 (#638)

Item 9 of the project read of 2026-11-09 (#629). JupyterLab's version
was written in three places that disagreed: `ganymede lab install`
pinned 4.6.4, CI's `lsp` job installed `jupyterlab==4.6.5`, and
ganymede-ui's `@jupyterlab/*` packages were 4.6.4. PyPI's latest is
4.6.6, so the weekly `pins` job had been failing. All three move to
4.6.6; ganymede-ui's in tlockney/ganymede-ui#455.

- `DEFAULT_VERSION` and `DEFAULT_SHA256` in `crates/ganymede-cli/src/lab.rs`
  are 4.6.6 and the SHA-256 PyPI lists for
  `jupyterlab-4.6.6-py3-none-any.whl`. `tests/lab.rs` with
  `GANYMEDE_E2E_LAB=1` downloads the wheel and checks it against the
  pin, so a wrong hash fails there.
- The validation scripts drove 4.6.6 in headless Chromium against
  `ganymede serve` and cdp-kernel: `login.mjs`, `trust.mjs`,
  `widgets.mjs` with `RELOAD=1`, and `jupyterlab.mjs`, as
  `scripts/test-workstation.sh` runs them. All four passed. The default
  extensions (`jupyterlab_widgets` 3.0.17, `anywidget` 0.11.0) are
  unchanged and still the latest.
- The docs name the default in two places a reader acts on,
  `docs/install.md` step 4 and `docs/frontends.md`. Each has an
  "Unreleased" note saying the latest release installs 4.6.4. This is a
  change to a released command, which needs no note by the rule, but
  without one the page would tell someone on the release that
  `ganymede lab remove 4.6.6` removes what they installed.
- Tests that build a stand-in bundle keep `4.6.4` as its version. They
  don't read the pin.

The three places still have to be moved by hand together. `pins` checks
the first against PyPI; nothing compares the other two with it.
