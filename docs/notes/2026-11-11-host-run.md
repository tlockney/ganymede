## 2026-11-11, host API: a notebook runs another (#664)

`notebooks.run` is `POST /api/notebooks/run` (#659) behind the host
API: `run.rs` now has one `run_notebook` both call, so the HTTP route,
`ganymede execute --results` and the host call agree on what a run
answers.

A run's kernel needs a grant before it can ask for anything, and its
kernel can answer `hello` before the call that started it learns its id.
So the server gives the run's kernel a launch variable,
`GANYMEDE_HOST_RUN`, naming the run, and looks the grant up by it. The
server reads its own record of the kernel's launch variables
(`RunningKernel::launch_var`), not the process's environment, so a
kernel can't take another run's grant. The grant is the intersection of
the caller's and the run notebook's, without `self.*`, since a run
writes nothing. The run also keeps every grant up its chain, and a
path must pass each of them with symlinks resolved: intersecting the
lists as text alone let a grant naming a symlink inside the caller's
folder reach the link's target. It is forgotten when the call ends, however it ends; a
run kernel with no grant left gets nothing.

Cancelling the call aborts its future: the run's kernel guard shuts the
kernel down and its run slot frees, as when an HTTP client goes away.
