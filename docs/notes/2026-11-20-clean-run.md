## 2026-11-20, Clean-run stamp (#898)

The journal view (ganymede-ui#184) shows "reproduced from a clean kernel"
when a notebook was last run top to bottom on a fresh kernel, and the
server kept no record of that. Now `notebook_run_all` writes
`metadata.ganymede.clean_run = {at, by, kernel}` and the room removes it
when a change makes the run stale.

Why a new notebook metadata key: it is the record #898 asks for. It is
ordinary notebook metadata under the `ganymede` key the server already
uses for cells, so no wire format changes: the REST and websocket API,
the Y document schema and the execute body are as before, and other
clients keep an unknown metadata key like any other. Unlike
`execution_by`, it is saved with the file.

Setting. `notebook_run_all` stamps only a run that restarted, finished
before its timeout, and in which every cell ended without a failure: the
worker reports whether it stopped, which an error, a reply of `aborted`, a
kernel that went or one that couldn't be reached all do (`run_and_wait`
returns it beside `finished`). The notebook as the run left it must also
be the one the run began with (no cell edited, added, deleted or moved
meanwhile), and the code cells with code must have an `execution_count`
each, in order, each one more than the one before. A restart leaves the
old counts and the execute endpoint doesn't clear them, so without that
a restart from another connection during the run, or an extra run of a
cell, would stamp (a probe found counts 1, 1, 2 stamped). A cell with an
error output stops the stamp too. The notebook is judged as read after the
run, before the outputs marked `keep_outputs: false` are dropped, since
dropping removes an error output the check needs. The stamp is written
after the drop as the run's last edit, inside one room edit
(`clean_run_edit`) that also checks the notebook still has the cells and
counts it judged, so an edit or run between the judgment and the stamp
leaves none. Any other `notebook_run_all` that runs cells removes the
stamp; one that fails before it runs (the restart fails, the room can't be
opened) leaves it as it was. The fake kernel gained an `abort` cell, which
replies `aborted` with no error output, for the test.

Clearing. `Room` keeps a second fingerprint beside the one for authorship
(`prints()`): `run_print()` hashes the ordered cell ids, each cell's type
and source, and a code cell's `execution_count`. `Room::receive` (a client
update) and `Room::edit` (a server edit) compare it before and after, and
only when the notebook holds a stamp, so a room without one pays nothing.
On a change the room removes `clean_run` in a further transaction and
sends it to every client, the sender included, and marks the document
dirty. Outputs, `execution_state`, cell metadata and notebook metadata are
not in the fingerprint, so writing the stamp, the outputs of the run and
`keep_outputs` marks never clear it. `Room::reload` and `merge_disk` don't
clear: the file is the notebook, stamp included. A Markdown cell's source
is in the fingerprint, since the issue says any later cell edit clears it.

The notebook's `metadata` is a shared map in the room whose values are
plain JSON, so `schema::set_clean_run` rewrites `ganymede` as a value (or
edits it in place when a client made it a shared map) and removes the
`ganymede` key when removing the stamp empties it.

Left open on #898: its "Run All after a restart" item. The app's own Run
All goes through JupyterLab's kernel connection, which the server can't
see, so a client's Run All after a restart can't set the stamp. A later
change could stamp from the client, or from an execute-endpoint run of
every cell after a restart. This change covers the MCP tool only.
