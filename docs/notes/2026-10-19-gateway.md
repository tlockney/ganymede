## 2026-10-19, remote kernels through a gateway (#167)

Thomas chose remote kernels for the iPad app first, with the on-device
kernel fast-tracked after. The server got `jupyter_server`'s gateway
client: `gateway_url` and `gateway_token` (flags `--gateway-url`,
`--gateway-token`; env `JUPYTER_GATEWAY_URL`,
`JUPYTER_GATEWAY_AUTH_TOKEN`).

- New crate `ganymede-gateway`. One `Gateway` value is the kernelspec
  source, provisioner and transport factory. `KernelspecSource::list` is
  synchronous, so it serves a cache that `refresh` fills; the server
  refreshes every minute, and the list is empty until the first success,
  so a server whose gateway is down still starts.
- A launch is `POST /api/kernels`. The process handle interrupts with
  `POST .../interrupt` (`InterruptMode::Signal`, so the session calls it)
  and kills with `DELETE`, so a restart is a new remote kernel. The
  factory finds the remote id by the address of the launched kernel's
  process handle, which avoids a kernel-host API change for one
  provisioner. kernel-host now exports `KernelProcess`.
- The transport is a websocket to `/api/kernels/{id}/channels` asking for
  `v1.kernel.websocket.jupyter.org`, falling back to the legacy JSON
  framing if the remote doesn't agree; both codecs already existed in
  `ganymede_protocol::ws`.
- TLS: reqwest's `rustls-no-provider` and tokio-tungstenite share one
  rustls config with the ring provider and the platform verifier. The
  `rustls` feature would pull in aws-lc, which needs cmake to cross-build
  for iOS.
- The server's `gateway` feature (default on) can be turned off; setting
  `gateway_url` without it is a startup error. Kernels an app passes in
  `Startup` win over `gateway_url`.
- Kernelspec resources (logos) aren't proxied yet.
- Tests: `ganymede-gateway/tests/remote.rs` drives an engine through a
  gateway to a real server with in-process fake kernels (start, execute,
  interrupt, restart, shutdown, wrong token); the server's
  `tests/gateway.rs` does the same over REST with `gateway_url`.
