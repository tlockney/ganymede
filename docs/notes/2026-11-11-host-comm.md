## 2026-11-11, host API: the comm and the read calls (#653)

The first step of [A host API for kernels](../host-api.md). A new crate,
`ganymede-host`, opens the `ganymede.host.v1` comm on a kernel subshell
once a kernel has answered, answers `hello` itself and hands every other
call to a `Responder`. `ganymede-api`'s kernel manager attaches it at
each boot and drops its traffic in `forward`, before the state tracking
and the client fan-out, so the busy and idle statuses around the host's
own messages don't move the kernel's execution state either. The server's
`HostApi` answers `notebooks.list`, `notebooks.read` and
`notebooks.search` with the `[host] read` grant, sharing the directory
walk and the search with the MCP tools.

Two choices worth knowing. The link is stored under the same lock the
pump checks, so no host message slips through to a client between the
comm opening and the link being in place. And host messages are told
apart by their parent's `header.session`, a per-link tag, rather than a
set of message ids, so the filter needs no bookkeeping as calls come and
go. The fake kernel gained subshells and a host client
(`host <method> <json>`), which the tests drive.

The engine (`ganymede execute`) doesn't open the comm yet; it needs the
file-based reads that the server gets from its contents manager.
