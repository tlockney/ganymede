# CLI and configuration

Every command, the server's flags and config file, environment
variables, logging, and exit codes. `ganymede <command> --help` prints the
same flags. The guides show them in use:
[Getting started](getting-started.md),
[JupyterLab and VS Code](frontends.md), and [Ganymede's app](app.md).

## Commands

| Command | Does |
| --- | --- |
| `kernelspec list`, `paths`, `install <dir>`, `remove <name>` | Find and manage kernelspecs, as `jupyter kernelspec` |
| `run` | Run code as cells and print the output |
| `console` | An interactive console on a kernel |
| `execute` (`exec`) | Run notebooks top to bottom, as `jupyter execute` |
| `nb clear` | Remove a notebook's outputs |
| `nb publish` | Write a notebook as one self-contained HTML page; see [Publishing a notebook](mcp.md#publishing-a-notebook) |
| `trust` | Sign a notebook as trusted, as `jupyter trust` |
| `grant` | A notebook's own [host API](#the-host-api) grant |
| `kernel` | Start a kernel and print its connection file, as `jupyter kernel` |
| `attach` | Run code on a running kernel by its connection file |
| `serve` | Serve the Jupyter REST and websocket API |
| `lab` | `serve` with JupyterLab, opened in the browser |
| `lab install`, `list`, `remove`, `clean`, `uninstall` | Manage JupyterLab bundles |
| `lab extension install`, `list`, `enable`, `disable`, `remove` | Manage prebuilt JupyterLab extensions |
| `ui`, `ui install`, `list`, `remove` | `serve` with [ganymede-ui](app.md#in-a-browser-from-ganymede) |
| `mcp`, `mcp call` | Notebook tools for coding agents over MCP on stdio, or one tool call from a script; see [Agents over MCP](mcp.md) |
| `info` | Versions and the directories in use |
| `completions <shell>` | Shell completions for bash, zsh, fish, powershell, elvish |

The kernel name `fake` is a built-in in-process kernel for trying things
out.

## Config file

A TOML file of the keys above, passed with `--config`. Without it,
`ganymede.toml` in the Jupyter config dir is read if it exists. Flags
override the file, and an unknown key is an error, so a misspelt `token`
can't start a server with a random one.

```toml
root_dir = "/srv/notebooks"
port = 9000
default_kernel = "cdp-node"
cull_idle_secs = 3600
allow_origins = ["https://notebooks.example.org"]
```

### The host API

`[host] read` lists the API paths that cell code may read through the
[host API](host-api.md): `notebooks.list`, `notebooks.read`,
`notebooks.search` and `notebooks.results`. A path covers itself and everything under it, by
whole segments, so `"journal"` covers `journal/a.ipynb` but not
`journal-private/`. The default, `[""]`, is the whole root; `[]` leaves
each notebook only itself. A path is matched where it leads once
symlinks are resolved, so a symlink in a granted folder doesn't reach
another.

`[host] edit_self`, on by default, lets a notebook add, edit and delete
its own cells (`self.add`, `self.edit`, `self.delete`), through its
document room, so every client sees the change. An edit or delete names
the cell's source hash from `notebooks.read`, and fails with
`source_mismatch` when the cell changed since. `false` takes the calls
away from every notebook that doesn't have its own grant.

`[host] run` lists the notebooks a notebook may run with
`notebooks.run`, matched as `read` is; the default, `[]`, is none. A run
uses `POST /api/notebooks/run`'s code: a fresh kernel from the
notebook's own kernelspec, the parameters in `GANYMEDE_PARAMS`, and
`{ path, status, results, error? }` back, with nothing written. Its
kernel gets the intersection of the caller's grant and the run
notebook's, and no `self.*` calls. Runs nest at most 3 deep, a kernel
has at most 2 runs in flight (more wait), and cancelling the call shuts
the run's kernel down.

A notebook's own grant replaces these defaults for the keys it sets.
`ganymede grant` stores it by the notebook's file id, beside the
server's file id database in the Jupyter data dir, so it follows a
rename made through the server and goes when the notebook is deleted
through it. A notebook deleted outside the server leaves its grant with
the path, so a new file saved there gets it; `--revoke` it first. A
running server sees a change on the next call; a `notebooks.run` keeps
the grant it started with until it ends.

```sh
ganymede grant journal/index.ipynb read=journal   # reads only journal/ (and itself)
ganymede grant downloaded.ipynb edit_self=false
ganymede grant journal/index.ipynb run=reports   # may run notebooks in reports/
ganymede grant --list                             # every notebook's grant
ganymede grant --revoke journal/index.ipynb read=journal
ganymede grant --revoke downloaded.ipynb          # back to the defaults
```

`read=PATH` adds a path to the notebook's own read list, which replaces
`[host] read` for it, so it can narrow the default or widen it; `run=PATH`
does the same for `[host] run`. Revoking every read path leaves the
notebook only itself; `--revoke NOTEBOOK read` (or `run`) goes back to
the default. `--root-dir` names the server's root when it
isn't the current directory, since grants are kept per root.

Clients such as the apps set the same grants over HTTP, with the
server's token:

```http
GET    /api/host/grants/journal/index.ipynb
PUT    /api/host/grants/journal/index.ipynb
{"read": ["journal"], "run": ["reports"]}
DELETE /api/host/grants/journal/index.ipynb
```

Each answers `{ path, grant, defaults }`: the notebook's own grant (`{}`
when it has none) and `[host]` from the config, which it replaces key by
key. `PUT` stores the grant in place of the one the notebook had, and
`{}` or `DELETE` removes it. A grant has only `read`, `edit_self` and
`run`; anything else is `400`, as are a grant path with `..` and a path
that isn't a notebook.
A missing notebook is `404`, and a server whose file ids live only in
memory answers `409`, since a grant there wouldn't outlive it. A kernel
holds no token, so it can't grant itself anything.

#### Under `ganymede execute`

> [!NOTE]
> **Unreleased.** Available only from a build of `main` (HEAD), not in
> the latest release.

`ganymede execute` answers its kernels' host calls too, with no server
running. API paths are relative to the current directory, and a
notebook under it is its kernel's own notebook. The defaults are
`[host]` from the config file, with `--grant` in place of each key it
names, and a notebook's own grant from `ganymede grant` (with the
current directory as its root) replaces them key by key, as on a
server. `--grant read=PATH` and `--grant run=PATH` are repeatable and
take paths as `ganymede grant` does; `""` is the whole current
directory. An executed notebook's kernel has no `self.*` calls, whatever
its grant, since `execute` writes the notebook itself when the run
ends. A `notebooks.run` starts its kernel from the kernelspecs `serve`
would use with the same config and `--kernelspec-root` flags, and shuts
it down when it answers. A config file that doesn't parse, like a host
that can't start, leaves the run without the host API, with a warning.

```sh
ganymede execute index.ipynb --grant read=journal --grant run=reports
```

## Static headers

`static_headers` adds response headers to files served from a
`static_dir` that isn't JupyterLab. Keys are paths under `base_url`; a
key ending in `*` matches every path that starts with the rest of it.
Keys match the request path, and also the path as the file is found:
percent-decoded, without empty or `.` segments, and with `index.html`
added to one ending in `/`. Nothing
is added by default. Routes the server answers itself, such as
`/api/status`, never get these headers; a request no route claims, such
as an unknown `/api/` path, falls through to the static files and can.
When several keys set the same header, the last key in sorted order
wins, and a configured header replaces one the server set. The
`frame_ancestors` directive is appended to a `Content-Security-Policy`
set here unless it already has a `frame-ancestors` directive, so a page
can set its own.

A page that needs `SharedArrayBuffer`, such as one hosting a
kernel in a web worker, must be cross-origin isolated:

```toml
[static_headers."/kernel.html"]
Cross-Origin-Opener-Policy = "same-origin"
Cross-Origin-Embedder-Policy = "require-corp"
```

An app embedding the server passes the same object in its JSON config
(`"static_headers": {"/kernel.html": {...}}`). The server refuses to
start when a key doesn't begin with `/` or a header name or value isn't
valid HTTP.

## Kernel crashes

A kernel that exits without being shut down or restarted, through the
API or by a client's `shutdown_request`, is restarted under the same id, in the same directory, as `jupyter_server`'s
`KernelRestarter` does. Its clients see:

1. For the request it was running, a reply with `status: error` and
   `ename: KernelDied` (and an `error` output, for a cell); for requests
   queued behind it, `status: aborted` replies. Each is followed by
   `status: idle`, so clients stop waiting for them.
2. `status: restarting`, which JupyterLab shows as an automatic restart
   and reconnects on.
3. The new kernel's own statuses.

A kernel that crashes again within ten seconds of being restarted counts
toward `kernel_restart_limit` (default 5). One crash past the limit, it
is reported `status: dead` and removed, as it always is with the limit
set to `0`. The kernel's state is lost in a restart, as it is under
Jupyter.

## Gateway

`--gateway-url` runs kernels on another Jupyter or Ganymede server while
notebooks and files stay local, as `jupyter_server --gateway-url` does:

```sh
ganymede serve --root-dir . \
  --gateway-url https://kernels.example.org --gateway-token "$TOKEN"
```

![Running kernels on another server. On your machine, a frontend talks to ganymede serve started with --gateway-url, which answers contents, sessions and trust from the notebook folder. For kernelspecs and kernels it calls the kernel server's REST API (kernelspecs, start, interrupt, restart, shut down) and relays each kernel's messages over its websocket. The kernel server, jupyter server or ganymede serve, runs the kernel processes over ZeroMQ.](images/architecture/gateway.svg)

Kernelspecs come from that server (`/api/kernelspecs`, refreshed every
minute); starting, interrupting, restarting and shutting down a kernel go
through its REST API, and kernel messages through its websocket. HTTPS is
checked against the system's trust store.

## Server info file

While it runs, `serve`, `lab` and `ui` write `jpserver-<pid>.json` in the
Jupyter runtime dir, as `jupyter_server` does, so tools that look for a
running Jupyter server find Ganymede too: `jupyter server list` lists it,
and an agent or script can read the URL and token from it instead of being
given them.

```json
{
  "base_url": "/",
  "ganymede_version": "0.9.0",
  "hostname": "127.0.0.1",
  "password": false,
  "pid": 41237,
  "port": 8888,
  "root_dir": "/Users/me/notebooks",
  "secure": false,
  "sock": "",
  "token": "3f9c...",
  "url": "http://127.0.0.1:8888/",
  "version": "2.21.1"
}
```

The keys are `jupyter_server`'s; `version` is the `jupyter_server`
version whose API Ganymede matches (as `GET /api` reports), and
`ganymede_version` tells a client it is Ganymede. `token` is empty when
auth is off. Beside it, `jpserver-<pid>-open.html` redirects a browser to
the server with the token. Both are readable only by you, since they hold
the token, and are removed when the server stops; a file left by a server
that was killed names a process that is gone, which `jupyter server list`
checks and cleans up. A server embedded in an app writes neither.

`lab` and `ui` open the browser on `jpserver-<pid>-open.html`, as
`jupyter_server` does, so the token is not in the browser command's
arguments. Snap and Flatpak browsers, the default Firefox and Chromium on
Ubuntu 22.04 and later, can't read the runtime dir and show an
access-denied page; `--no-redirect-file` opens the URL itself instead, as
`jupyter_server`'s `use_redirect_file = False` does.

## Environment variables

| Variable | Effect |
| --- | --- |
| `JUPYTER_CONFIG_DIR` | The Jupyter config dir. Default `~/.jupyter`. |
| `JUPYTER_DATA_DIR` | The user Jupyter data dir, where kernelspecs and signatures are. |
| `JUPYTER_PATH` | More data dirs to search for kernelspecs, first. |
| `JUPYTER_RUNTIME_DIR` | Where connection files, the cookie secret and the [server info file](#server-info-file) go. Default: `runtime/` in the data dir. |
| `JUPYTER_GATEWAY_URL`, `JUPYTER_GATEWAY_AUTH_TOKEN` | `--gateway-url` and `--gateway-token` when not given. |
| `GANYMEDE_DATA_DIR` | Where `lab install` and `ui install` put what they download. |
| `GANYMEDE_PYPI_URL`, `GANYMEDE_PYPI_HOSTS` | A PyPI mirror, and more hosts allowed to serve wheels; see [What a download trusts](frontends.md#what-a-download-trusts). |
| `GANYMEDE_UI_URL` | A mirror of ganymede-ui's release downloads. |
| `GANYMEDE_CRASH_REPORTING` | `1` turns crash reporting on and `0` off, overriding `crash_reporting`; see [Privacy and crash reporting](privacy.md). |
| `RUST_LOG` | The log filter, when `--log-level` isn't given. |
| `HTTPS_PROXY` | Used for downloads. |

`ganymede info` prints every directory in use.

### What a kernel gets

A kernel inherits the server's environment, then its kernelspec's `env`,
and gets two more, as under `jupyter_server`:

| Variable | Value |
| --- | --- |
| `JPY_PARENT_PID` | The server's process id. |
| `JPY_SESSION_NAME` | For a kernel started for a notebook (a session): the notebook's path on disk, so code can find the notebook it runs in. A session renamed or moved changes it on the kernel's next restart. For a kernel started on its own: the kernel id. |

### Parameters and named results

`ganymede execute -p` and `--results` make a notebook a program:
parameters in, named results out. Neither names a language; any kernel
that reads the variable and writes the MIME type takes part.

| What | Format |
| --- | --- |
| `GANYMEDE_PARAMS` | Set on every kernel `execute` and `POST /api/notebooks/run` start: the parameters from `-p` and `--params-file` as one JSON object, at most 32,767 bytes, or `{}` without them, so a kernel never inherits a parent run's. The executed notebook records them in `metadata.ganymede.params`, and a run without them removes that key. |
| `application/vnd.ganymede.result+json` | A named result: a `display_data` or `execute_result` output whose bundle holds `{ "name": string, "value": JSON }`. Add a `text/plain` entry for frontends that don't know the type. |
| `application/scrapbook.scrap.json+json`, `application/scrapbook.scrap.text+json` | Python scrapbook's scraps (`sb.glue`), read as named results from their `name` and `data`. |

When a name appears more than once, the last output wins, as in
scrapbook. `--results` prints one JSON line per notebook: `{"path",
"status": "ok" | "error", "results": {name: value}, "error"?}`. The
results come only from cells the run executed, so a failed run reports
what it published before the failure, never what an earlier run saved in
later cells or in cells skipped by tag. A run that stops on a signal, or
whose notebook can't be saved, prints its line and ends the command.

`POST /api/notebooks/run` is the same over HTTP, for clients such as the
apps' links and Shortcuts:

```http
POST /api/notebooks/run
{"path": "reports/daily.ipynb", "params": {"day": "2026-11-10"}, "timeout": 600}
```

It runs the notebook in a fresh kernel from its own kernelspec, with
`params` (a JSON object, optional) in `GANYMEDE_PARAMS`, and answers when
the run ends with the body of one `--results` line. `path` is an API
path; the notebook is read from its room when one is open, so unsaved
edits run. Nothing is written: not the notebook, not its room, and
`save` takes only `false`. `timeout` is in seconds for the whole run, at
most and by default 3600. The run's kernel is listed in `/api/kernels`
while it runs, and shut down when the run ends, times out, or the client
disconnects. A missing `path`, bad `params` or `timeout`, or a notebook
with no `metadata.kernelspec.name`, or one this server doesn't have, is
`400`, and a notebook that can't be
read `404`, before any kernel starts; after that, a failure is `200` with
`"status": "error"`.

## Logging

`serve`, `lab` and `ui` log at info level on stderr; `-v` raises it to
debug, and `RUST_LOG` overrides both. `--log-level` (`trace`, `debug`,
`info`, `warn`, `error`, or Jupyter's `WARNING` and `CRITICAL`)
overrides all three, and `--log-file` appends the log to a file instead
of stderr. Kernels' own output lines start with
`[kernel <first 8 of its id>]`.

## Exit status

| Status | Meaning |
| --- | --- |
| 0 | Success |
| 1 | A cell failed, a kernel timed out or died, or a file or download failed (as `jupyter execute`) |
| 2 | Usage error: an unknown flag, a missing argument, no code to run |
| 128+N | Stopped by signal N: 130 for Ctrl-C, 143 for SIGTERM, 129 for SIGHUP |
