Before you start

How to read this

This primer explains how Ganymede's code fits together across its three active repositories (ganymede, cdp-kernel, ganymede-ui), so you can pick any part and dive in already knowing where it sits, why it exists and which files to open first. It is written for an experienced engineer who is new to this codebase. It describes main as of the date above.

Each chapter follows the same shape:

  • Why it exists: the problem the part solves and what it deliberately does not do.
  • How the code is laid out: crates, modules and files, with sizes where they help you judge effort.
  • Flows: one or two real paths traced through named files, such as running a cell or an agent editing a live notebook.
  • Dive in: where to start reading, and which user docs already go deeper.

The primer does not repeat the user docs. Where a topic is already covered well, it links to the page. The most useful ones to keep open are ganymede's architecture, rooms and host API pages, ganymede-ui's architecture, and cdp-kernel's architecture.

One habit worth knowing from the start: almost every Rust module and many TypeScript files open with a doc comment (//!) that states the module's contract, its edge cases and the issue it came from. Reading those headers is the fastest way through the code, and this primer points to them often.

Chapter 1 of 14

The map

Ganymede is a Rust replacement for the middle of the Jupyter stack, jupyter_server. It keeps both of that server's interfaces: the REST and websocket API above it, and the kernel messaging protocol over ZeroMQ below it. Everything else in the project is either a client of that API (the web UI and the apps) or a kernel behind it (cdp-kernel).

Three layers

  • Clients call the Jupyter REST and websocket API. JupyterLab and VS Code work unchanged. ganymede-ui's web app is a client too, and so are agents, through MCP or the host API. No client gets a private side door into the core.
  • The Rust core (repo ganymede) is the server: kernel lifecycle, notebook files, live document rooms, runs, the host API and MCP. It knows no kernel language.
  • Kernels run code. Any Jupyter kernel works, launched from its kernelspec. cdp-kernel is the first-class one, for TypeScript and JavaScript.

Four repositories

Repo Language What it holds Size of the main code

tlockney/cdp-kernel TypeScript The kernel (src/) and the code it injects into each runtime (runtime/) About 40 files in src/, 20 runtime modules

The repos are joined at four points. ganymede-ui pins a ganymede commit or tag (GANYMEDE_REF in its ci.yml) and links ganymede-ffi built from it as an XCFramework. ganymede-ui depends on @tlockney/cdp-kernel from npm for the in-page kernel. ganymede launches cdp-kernel like any other kernel, from a kernelspec. ganymede's docs site copies ganymede-ui's docs and cell API reference at build time.

Arrows point from a repo to what it uses. The XCFramework is built from the ganymede commit in GANYMEDE_REF, so an app change that needs a server change waits for that pin to move.

Where it runs

The same crates run in four setups (architecture: where it runs has the picture):

  1. Workstation or server: ganymede serve or ganymede lab as a process, kernels as child processes over ZeroMQ.
  2. Mac app: the server runs inside the app's process through ganymede-ffi, on loopback, and the web view loads ganymede-ui from it. Kernels are the Mac's kernelspecs, plus cdp-kernel in a hidden web view registered with the server.
  3. iPad and iPhone app: the same app. iOS won't let an app launch processes, so the only local kernel is cdp-kernel in a hidden web view; others come from a remote server through the gateway.
  4. Browser only: ganymede-ui alone, notebooks in IndexedDB, kernels in Web Workers. The Rust core is not involved.

Rules that shape the code

  • Only the core is Rust. UIs are API clients and live outside the ganymede repo.
  • The host knows no language. Nothing in the host crates special-cases Python or TypeScript; language facts come from the kernelspec, kernel_info_reply and output MIME types. The test suite runs the same scenarios against cdp-kernel and ipykernel.
  • The Jupyter API is a compatibility target. A difference from jupyter_server is a bug. The e2e suite runs jupyter_server 2.21.1 side by side to check.
  • Conservative security defaults. Grants and permissions are scoped as narrowly as possible, and nested runs can only narrow them.
  • The bottom crates do no I/O, so they build for any target, including wasm and iOS.

Chapter 2 of 14

Pure foundations: protocol and nbformat

Two crates sit at the bottom and do no network or file I/O: ganymede-protocol models the Jupyter messages and their byte layouts, and ganymede-nbformat models the .ipynb file. Because they do no I/O, they build for wasm and iOS, and every higher crate can trust one definition of a message and of a notebook. (ganymede-documents, the third no-I/O crate, belongs to rooms and is in chapter 6.)

ganymede-protocol (about 1,350 lines)

It answers one question: given a message, what bytes go on each kind of wire, and back.

File What it holds
message.rs Message (header, parent header, metadata, content, binary buffers), Header, the Channel enum. Protocol version 5.5, including subshell_id
content.rs Typed content only for messages the host itself reads or sends: execute_request, kernel_info_reply, status, stream and so on. Everything else stays raw JSON
wire.rs ZeroMQ multipart framing: identities, the <IDS|MSG> delimiter, an HMAC-SHA256 signature, then header, parent header, metadata, content and buffers. Signs and verifies frames
ws.rs The two websocket framings clients use on /api/kernels/{id}/channels: v1.kernel.websocket.jupyter.org (binary, an offset table then the parts) and the legacy JSON form
connection.rs The connection file a host writes for a kernel: ports, transport, key, signature scheme

Two design rules run through it, stated in lib.rs:

  • Unknown fields survive. Every struct has a #[serde(flatten)] extra map, so a field a kernel adds (a capability list in kernel_info_reply, say) reaches clients untouched.
  • Content is kept as JSON on Message and parsed into a typed struct only on demand (Message::content_as). The server mostly forwards messages, so it avoids parsing what it doesn't need.

Lenience is deliberate too: a header missing username, date or version is accepted, because jupyter_client accepts it and rejecting it would drop a reply the host is waiting for.

ganymede-nbformat (about 6,700 lines)

Its core promise is in the crate doc: a notebook saved by Ganymede is byte for byte what Python's nbformat would write, so saving never produces a spurious git diff. The rest of the crate has grown into the toolkit for anything that turns a notebook into something else.

File What it does
types.rs Notebook, Cell, Output, MimeBundle, each with an extra map; unknown cell and output types are kept verbatim
reader.rs Lenient reading, as Python's nbformat: string or list multi-line text, nulls read as defaults, missing or duplicate cell ids repaired. ReadReport says what was repaired
upgrade.rs nbformat 3 upgraded to 4 on read
writer.rs The byte-identical writer: split lines, strip transient metadata, sort keys, indent 1, Python's float formatting (python_float_repr), trailing newline
atomic.rs atomic_write: temp file then rename. Shared with the contents layer
params.rs, results.rs The run contract's data side: parameters go to the kernel in GANYMEDE_PARAMS; named results are outputs of type application/vnd.ganymede.result+json (scrapbook's types are read too)
html.rs, highlight.rs ganymede nb publish: one self-contained HTML page with no scripts from the notebook, HTML outputs in sandboxed iframes, server-side syntax highlighting
export.rs Script and Markdown export, the two nbconvert formats that need no templates

Note what params.rs and results.rs do not do: they never mention a language. A parameter is JSON in an environment variable, and a result is a MIME type in an output. Each kernel decides how to expose them; cdp-kernel reads them as jupyter.params and writes them with jupyter.result.

Dive in

  • Read ganymede-protocol/src/lib.rs and wire.rs first; they are short and set the vocabulary for chapter 3.
  • For nbformat, tests/roundtrip.rs shows the byte-for-byte promise being checked, and tests/lenient.rs lists the malformed inputs it tolerates.
  • docs/protocol.md covers what a host must get right in the protocol and what is usually missed.

Chapter 3 of 14

Kernel host: getting a kernel and talking to it

ganymede-kernel-host (about 6,500 lines) is Ganymede's jupyter_client. It finds kernels, launches them, connects to them and runs the per-kernel state machine. It is built around three seams, so the same code drives a local process over ZeroMQ, a kernel on another server, and a kernel the iPad app runs inside a web view.

The seams

A kernel comes to life in three steps, each behind a trait:

  1. KernelspecSource (kernelspec.rs) lists what can be launched. FsKernelspecs searches the Jupyter data directories in jupyter_client's order, plus extra roots from --kernelspec-root. That is how conda and venv kernels are found without the host knowing what a venv is.
  2. Provisioner (process.rs) makes a kernel exist and returns a LaunchedKernel: its connection info (if any) and a KernelProcess handle for interrupt and kill. SubprocessProvisioner allocates five ports, writes the connection file in the runtime directory and spawns the kernelspec's command. attach adopts a kernel that is already running.
  3. TransportFactory (transport.rs) turns a LaunchedKernel into a KernelTransport: a TransportSink to send on and a stream of (Channel, Message) coming back. ZmqTransport (zmq.rs) uses the pure-Rust zeromq crate: DEALER sockets for shell, control and stdin, SUB for iopub, REQ for heartbeat, one task per socket.

Two other implementations fill all three seams at once:

  • ganymede-gateway (one 600-line file): kernels on another Jupyter server. Its kernelspecs are the remote GET /api/kernelspecs, launch is POST /api/kernels, and the transport is the remote channels websocket. This is --gateway-url, and how the iPad app reaches a Mac's kernels.
  • registered.rs: kernels an app runs itself. The app implements AppKernel (start, send, stop) and pushes messages back with RegisteredKernels::deliver. No process, no ZeroMQ. The Apple apps register cdp-kernel running in a hidden web view this way, through ganymede-ffi, so it appears in /api/kernels beside every other kernel (chapter 12).

The Cargo features zmq and subprocess are on by default. Without them the crate is the state machine, kernelspec parsing and the in-process transport, which is what builds for iOS and wasm.

Read each row left to right: the same three questions get a local, a remote or an in-app answer, and KernelSession on the right never knows which.

KernelSession: the state machine

session.rs (about 1,800 lines) is the heart of the crate. One KernelSession wraps one connected kernel and knows what a plain message pipe does not:

  • The startup nudge (nudge). ZeroMQ's PUB/SUB silently drops messages published before the subscriber connects. So the host sends kernel_info_request on shell and control until both answer and at least one iopub message has arrived. A kernel with an XPUB socket (ipykernel 7) sends iopub_welcome, which settles the iopub half at once.
  • Two-part completion. A request is done when its reply has arrived on shell and an iopub status: idle with the request as parent has arrived. They come on different sockets, in either order. The Pending struct tracks both.
  • Routing. Replies go to the requester by parent_header.msg_id; iopub fans out to every subscriber (subscribe, or subscribe_lossless for consumers that must not miss a message).
  • Interrupt by signal or by interrupt_request, as the kernelspec's interrupt_mode says. Shutdown sends shutdown_request, waits a grace period, then kills.
  • Death: the process exiting, the transport closing, or missed heartbeats for a kernel with no process handle.

Crash restarts are not here: they belong to the kernel manager in ganymede-api (chapter 4), which restarts a crashed kernel under the same id up to restart_limit times, as jupyter_server's restarter does. A kernel the platform ended (lost, as iOS does to the app's kernel in the background) has its own limit: three losses within 60 seconds of each other restart it, and the next leaves it dead, with the reason on status: dead.

FlowStarting a kernel

  1. The kernel manager picks a Kernelspec from the KernelspecSource.
  2. Provisioner::launch reserves five ports (in-process and in a per-user directory, so two Ganymede processes don't hand out the same port), writes kernel-<id>.json, and spawns the command with the connection file path substituted.
  3. TransportFactory::connect opens the five sockets.
  4. KernelSession::start begins reading; nudge runs the handshake and stores kernel_info_reply.
  5. The session is live: clients can send on shell, and iopub flows to all of them.

Dive in

  • Start with lib.rs (84 lines) for the seams, then transport.rs (78 lines), then session.rs.
  • testing.rs is a fake kernel over the in-process transport. It speaks the protocol and no language, and is the quickest way to see the state machine exercised.
  • process.rs is long because of platform detail: port reservation, process groups, and Windows job objects so a kernel's children die with it.
  • The design note for registered kernels is docs/in-app-kernel.md.

Chapter 4 of 14

API and contents: the server's logic without HTTP

Two crates hold the logic behind jupyter_server's REST API, with no HTTP in either. ganymede-api manages kernels, sessions and per-client connections; ganymede-contents manages files. The HTTP server (chapter 5) is a thin mapping onto them. They were kept free of HTTP so an app could call them directly; in practice the apps run the full server on loopback instead, which turned out simpler, but the split still keeps the logic testable on its own.

ganymede-api (about 3,800 lines)

File What it holds
kernels.rs KernelManager: start, restart, interrupt, shut down, cull idle kernels, list. Crash restarts under the same id up to restart_limit (default 5), as jupyter_server's KernelRestarter. A lost kernel restarts at most 3 times within 60 s, then stays dead and says why. Holds a weak reference to the host API responder (set_host)
sessions.rs SessionManager: Jupyter sessions, a notebook path bound to a kernel. notebook_of_kernel is how the host API and MCP find which notebook a kernel belongs to
bridge.rs ClientConnection: one websocket's share of a kernel's traffic
kernel_log.rs The last lines of each kernel's stdout and stderr, for GET /api/kernels/{id}/log. A Ganymede extension, so a client can show why a kernel died
models.rs The JSON models, field for field as jupyter_server returns them

The bridge is the part worth understanding. jupyter_server gives each websocket its own DEALER sockets to the kernel. Ganymede shares one set of sockets per kernel and dispatches each incoming message to per-client queues instead: iopub to everyone, replies only to the client whose session is in the parent header. It keeps jupyter_server's behaviors on top of that:

  • When the last client disconnects, its queue keeps filling. A client that reconnects with the same session_id gets the buffered messages, so a laptop waking from sleep sees what ran while it was away.
  • A new connection with the session id of an open one replaces it, since the old one is most likely a dead socket.
  • Reply queues are unbounded, so a slow client never loses its own execute_reply. Iopub beyond a limit is dropped, and the client is told with a stderr stream message.

One gotcha from the host API work: KernelManager holds the host responder weakly. A strong reference formed a cycle that kept embedding apps alive after they stopped the server.

ganymede-contents (about 5,900 lines)

The contents API: files, directories, checkpoints. Its design comes from the iPad case, where the notebook folder is in iCloud Drive and other writers touch the same files.

File What it holds
lib.rs The Contents trait and the wire model (ContentsModel, SaveRequest, Checkpoint)
fs.rs FsContents, the local filesystem implementation
paths.rs ApiPath::parse, the only way client input becomes a path. It rejects anything that could leave the root before any filesystem call
fileid.rs FileIds: a stable id per file, kept in SQLite, moved by renames through the API. Rooms are keyed by these ids. Host API grants are stored here too, so they follow a rename, each with a stamp of its file (size, mtime, inode) so a grant is dropped when its file changes outside Ganymede
trust.rs Notebook trust, compatible with Jupyter's own nbsignatures.db: a notebook Jupyter trusts is trusted here, and the other way round

The rules: files are the source of truth and nothing is cached. Writes are atomic (temp file, fsync, rename). The checkpoint directory can live outside the root, so checkpoints aren't synced with notebooks.

FlowSaving a notebook

  1. A client sends PUT /api/contents/{path} with the whole notebook, and either If-Match with the ETag it read or last_modified in the body.
  2. paths.rs parses the path; fs.rs reads the file on disk now.
  3. If the sha256 doesn't match If-Match, the answer is 412. If the file is more than 500 ms newer than last_modified, it is 409. Nothing is written either way: that is how an edit from another device isn't overwritten.
  4. The notebook is validated through ganymede-nbformat, written to a temp file in the same directory, fsynced and renamed over the old file.
  5. trust.rs signs it if every code cell is trusted. The first checkpoint is created if there is none.
  6. The answer is 200 or 201 with the model and its new ETag.

With rooms on (chapter 6), most saves no longer come from clients: the room's own task saves the live document, through this same path, with If-Match on the hash it last wrote. The architecture page's save diagram shows the client path.

Dive in

  • ganymede-api/src/lib.rs (65 lines), then bridge.rs for the per-client queues.
  • ganymede-contents/src/lib.rs has the whole contract in its header; paths.rs is the security boundary for file access.

Chapter 5 of 14

The server

ganymede-server is the biggest crate (about 29,000 lines with tests, 18,000 in src/). Its own description is "every handler is a thin mapping from a route to an API call", and that holds for the Jupyter API. Most of its size is in the Ganymede extensions that have no jupyter_server equivalent: rooms, MCP, the host API, runs.

Code map

Two neighbor crates fill specific routes: ganymede-terminals (/api/terminals, the user's shell in a pseudo-terminal) and ganymede-lsp (/lsp/*, language servers started on demand and shared by every client). Neither exists on iOS or wasm.

Who gets in

Every request passes auth.rs, which does what jupyter_server does and adds two ways in:

  • The token, in an Authorization header or ?token=, traded for a signed login cookie in tornado's format, with _xsrf on cookie requests that change state. The apps start their server with a new random token each launch.
  • mcp_token, a second token that only /mcp accepts and that sets no cookie, so an agent given it can't reach the REST API. The Mac app gives agents this one.
  • A tailnet identity (tailscale.rs, off by default). With [tailscale] allow listing logins or tags, a request gets in without a token when tailscale serve names its sender on loopback, or when tailscale whois says which login or tagged device owns the peer's tailnet address. The name shows in /api/me, in the log, and in the room's credit for edits (chapter 6). /mcp doesn't accept it, and a browser request needs same-origin fetch metadata, so another site can't ride on it. Programs such as the gateway (chapter 3) mark their requests with a Ganymede-Client header.

A Host check against DNS rebinding runs before any of these, and the server refuses to start with tailnet identity on and that check off.

How a request is served

serve.rs builds the KernelManager, SessionManager and FsContents from config, or from what the embedder passed in Startup, wraps them in AppState, and hands that to routes::router. Routes nest under base_url. Requests pass the auth layer, then a handler calls into ganymede-api or ganymede-contents, and blocking filesystem work goes through a blocking helper onto tokio's blocking pool. Anything not matched falls through to JupyterLab or --static-dir (which is how ganymede-ui is served).

GET /api reports jupyter_server version 2.21.1, the version whose API this server matches. Clients use it to decide what they're talking to.

FlowRunning a cell

  1. A client opens /api/kernels/{id}/channels?session_id=…. ws.rs picks the v1.kernel.websocket.jupyter.org framing if the client offers it, legacy JSON otherwise, and attaches a ClientConnection from ganymede-api/bridge.rs.
  2. The client sends an execute_request frame. ganymede-protocol::ws decodes it into (Channel::Shell, Message).
  3. The bridge notes the client's session and calls KernelSession::send, which ZmqTransport writes to the kernel's shell socket, signed with the connection key.
  4. The kernel publishes status: busy, execute_input, outputs, then status: idle on iopub. The session fans these out; the bridge puts each in every client's queue, so a second tab sees the same outputs.
  5. The execute_reply comes back on shell, before or after idle. The bridge sends it only to the client whose session is in its parent header.
  6. If the cell calls input(), an input_request on stdin goes to the requesting client, which answers with input_reply.

Each dot is a layer the message passes through. KernelSession marks the request done only once both the reply (3) and its idle status (2) have arrived.

The architecture page has the same flow as a message sequence.

Chapter 6 of 14

Rooms: one live notebook for everyone

A room is a notebook held live in the server as a Yjs document (the Rust port, yrs), which every client edits at once: JupyterLab with its collaboration extension, ganymede-ui, an agent through MCP, and the server's own cell runner. The room, not any client, owns the file: it loads it, autosaves it and merges in changes other programs make. Rooms are what make priority 3, a person and an agent in one live notebook, possible, and the apps have opened notebooks through rooms since ganymede-ui 0.10.0.

The protocol is jupyter-collaboration's, so JupyterLab's own collaboration extension works against Ganymede unchanged.

Two halves

ganymede-documents (about 2,900 lines, no I/O) is the pure part:

File What it holds
room.rs Room: one document and its connections as a state machine. The host feeds it frames and connection events; it returns Effects (frames to send, saves to make). Speaks y-websocket: sync, awareness, and jupyter-collaboration's raw save message. Also keeps, in memory, who last changed each cell (Author), for the agent tools (chapter 8)
schema.rs Maps a ganymede_nbformat::Notebook to and from the Y document shape @jupyter/ydoc expects
merge.rs Three-way merge (base, room, disk), cell by cell by id, part by part (source, outputs, each metadata key). Where both changed the same part, the disk wins that part

The server side does the I/O:

File What it holds
collab.rs (2,650 lines) /api/collaboration/session/{path} (gives the file id) and /api/collaboration/room/{format}:{type}:{fileId} (the websocket). Each room is one tokio task, run_room, that owns the Room and the file
watch.rs Watches the file's parent directory, not the file, since saves by rename leave a file watch on the old inode
room_lock.rs One server per machine owns a notebook's room, by an OS file lock in the runtime directory. A second server's room is read-only until the owner closes
execute.rs POST /api/kernels/{id}/execute: run cells by id and write outputs into the room

What a room's task does

  • Load the notebook through Contents, and record the file's hash.
  • Apply client updates (after depth.rs) and broadcast them to the other connections.
  • Autosave one second after the last edit, with If-Match on the hash it last read or wrote, so it never overwrites a file that changed since.
  • Watch for outside changes: file events debounced by half a second, plus a poll every ten seconds (every second where there are no file events). A change whose hash is the room's own last save is ignored. Any other change is merged: a clean room just reloads; a room with unsaved edits keeps them, takes the disk's changes to other cells, and saves the merge.
  • Close a minute after its last client leaves, saving first.
  • Trust: the room signs the notebook when it saves, if every code cell's outputs came from a run on this server. Outputs read from an unsigned file stay untrusted until the cell runs again or someone trusts the notebook.

JupyterLab and ganymede-ui sync both ways over y-websocket. The MCP tools and the execute worker run inside the server and edit the room directly. Only the room's task touches the file, which is why two writers can't overwrite each other.

FlowAn edit in a room

  1. ganymede-ui's notebook pane (src/lib/room.ts) sends PUT /api/collaboration/session/{path} and gets the file id.
  2. It opens the room websocket for json:notebook:<fileId> with y-websocket, and syncs.
  3. Typing in a cell produces a Yjs update. collab.rs hands the frame to Room, which applies it and returns effects: the update for every other connection.
  4. JupyterLab, or an agent following the room, gets the update and shows the edit.
  5. A second later the room task writes the notebook through ganymede-contents, atomically, with If-Match.

FlowRunning cells into a room

An agent or a Shortcut has no websocket, so it can't follow the room to see outputs. execute.rs solves that: the client posts cell ids and each cell's source hash (MurmurHash2, seed 0). The room checks every hash against the current source (409 source_mismatch if the cell changed since the client read it), clears the cells, marks them running and queues the batch, all in one step of its task. One worker per room runs the queue on the kernel through ganymede-exec and writes outputs into the room as they arrive, so they reach every client and the file even with no client connected. An optional wait returns the finished cells. A client can also leave out the hash and run whatever the room holds, name cells by tag, or send "cells": "all". The room resolves these in the same step as the checks, so a notebook with no cell ids on disk (nbformat 4.4) runs by the ids the room gave it, and an unknown id or tag refuses the whole batch.

The hash check is the pattern to recognize across the code: a writer names the version it read, and loses if someone else changed it. The host API's self.edit and self.delete use it too.

Chapter 7 of 14

The notebook as a program

Priority 1 is a notebook that takes parameters, returns named results, and can be run from anywhere: the CLI, HTTP, an app link or Shortcut, or another notebook. In code this is three pieces: a headless executor (ganymede-exec), one run function shared by every entry point (run.rs), and the host API that lets a kernel call back into the server under grants (ganymede-host plus host.rs). User docs: programs.md and host-api.md.

ganymede-exec (one 1,700-line file)

Ganymede's nbclient. It runs a notebook's code cells on a KernelSession and turns iopub messages into nbformat outputs, reproducing nbclient's defaults so a notebook executed here and by jupyter execute differ only in timestamps: display_id updates rewrite every matching output, clear_output(wait) clears on the next output, widget state lands in metadata.widgets, the raises-exception and skip-execution tags are honored. NotebookRun is used three ways: by ganymede execute (through ganymede-engine), by run.rs, and by the room's execute worker (chapter 6), which writes outputs into the room as they arrive.

The run contract

  • Parameters in: a JSON object in the GANYMEDE_PARAMS environment variable, recorded in metadata.ganymede.params (ganymede-nbformat/params.rs). The kernel exposes it; cdp-kernel as jupyter.params.
  • Results out: outputs of type application/vnd.ganymede.result+json holding {name, value} (results.rs). cdp-kernel writes them with jupyter.result(name, value).
  • Fresh kernel from the notebook's own kernelspec, top to bottom, then shut down.
  • Read from the room when one is open, so unsaved edits run. Neither the notebook nor its room is written. save: "copy" keeps the executed notebook under runs/<path>/<UTC time>.ipynb.

POST /api/notebooks/run and the host API's notebooks.run share run_notebook in run.rs; app links and Shortcuts call that endpoint on the app's own server. ganymede execute takes the same contract through ganymede-engine, which also wraps ganymede-exec.

Four doors, two code paths, one executor. Only the host API door checks the caller against a grant, because there the caller is a kernel; at the other doors it is a person or a token holder (and an app link asks the person the first time). Whatever the door, the run's own kernel gets the grant of the notebook it runs.

The host API

The problem it solves: code in a cell wants to read or run other notebooks, but giving a kernel the server's token would give it everything. Instead the server opens a comm (ganymede.host.v1) to each kernel and answers calls on it, checking what that kernel's notebook was granted. The kernel never holds a credential.

ganymede-host (about 440 lines) is the language-free transport. attach joins a KernelSession once the kernel answers, asks for a kernel subshell (protocol 5.5) so a cell that is awaiting a call still gets the reply, and opens the comm. Calls arrive as comm_msg on iopub ({id, method, params}); replies go back on the subshell. HostLink::is_host_message lets the bridge hide this traffic from other clients. The crate knows no method but hello; a Responder answers the rest. A kernel that doesn't support subshells gets no comm, because an awaited call could never be answered.

host.rs in the server is the Responder: notebooks.list, read, search, results, run, and self.add, self.edit, self.delete on the kernel's own notebook through its room. These share code with the MCP tools: the tools render answers as text for a model, the host API returns JSON.

Grants

A grant says what a notebook's kernel may ask for: read paths, run paths, and edit_self. Defaults come from [host] in the config (read the whole root, edit itself, run nothing). Per-notebook grants are stored by file id in the file id database, so they follow a rename; they're set with ganymede grant or the apps' Notebook Access sheet, never by the notebook itself. A file replaced outside Ganymede (git, Finder, sync) keeps its path's file id, so each grant also carries a stamp of its file (size, mtime and, on Unix, inode): a checked read drops the grant when the file no longer matches. The server's own saves restamp it through stamping.rs, which wraps Contents, and renaming or deleting a folder moves or drops the grants inside it. A notebook can list what it wants in metadata.ganymede.host.wants, which a client shows but which grants nothing.

The security rule worth remembering: grants only narrow. A notebook run from another gets the intersection of its own grant and every caller's up the chain. Runs nest at most 3 deep and each kernel has at most 2 runs in flight. Paths are matched by whole segments after symlinks are resolved.

FlowA notebook running another notebook

  1. A cell calls await jupyter.host() and then host.notebooks.run({path, params}). cdp-kernel (runtime/host.mjs) sends a comm_msg with {id, method: "notebooks.run", params}.
  2. The kernel manager's fan-out spots it as host traffic (ganymede-host) and hands it to the responder instead of the clients.
  3. host.rs finds the kernel's notebook (SessionManager::notebook_of_kernel, then its file id), loads that notebook's grant, and checks run against the target path.
  4. It calls run_notebook (run.rs), which starts a fresh kernel with GANYMEDE_PARAMS set and a launch variable naming the run, so the inner kernel's own grant is the intersection.
  5. ganymede-exec runs the target top to bottom; named_results collects its results.
  6. The reply {path, status, results} goes back on the caller's subshell, and the awaiting cell resumes.

Agent-native: an agent in the same live notebook

Priority 3 is a person and an agent working in one live notebook. The server makes this possible by exposing notebooks to agents over the Model Context Protocol (MCP), with tools that edit the same room (chapter 6) a person has open in the app or JupyterLab. Design choices visible in the code

  • Output for a model, not a browser. Answers use nb-cli's format: an @@cell line with index, id and type, the source, then an @@output line per output as plain text. HTML is stripped, ANSI colors removed, tracebacks trimmed, and output over 4,000 characters goes to a file named by its sha256, whose path is returned instead.
  • Provenance. Cells an agent writes carry metadata.ganymede.agent = {by, mode, at}, where mode is executed (ran in the kernel), recorded (a step that ran elsewhere, such as a shell command) or note. cell_edit keeps the replaced source in a history.
  • Scratch runs. cell_run with record: false runs in the kernel, sharing its state, and leaves nothing in the notebook.
  • Cells by id, never by index, so concurrent edits don't shift the target.
  • One set of room edits. The tools, the execute endpoint and the host API's self.* calls (chapter 7) all edit cells through room_ops.rs, so they can't drift. The tools render text; the host API returns JSON.

How the agent hears about a person's edits

The room records who last changed each cell (Author in room.rs, kept in memory, not in the file): the name a client sent in its awareness state (the Mac app sends the person's full name, JupyterLab its user name), a tailnet login (chapter 5), or a name the server's caller gives for its own edits. Four mechanisms build on that:

  • A pointer on every reply. When others changed or ran cells since the agent's read mark, the tool's reply ends with an @@changed line naming who. The agent calls notebook_read(since) for the detail.
  • The edit check. cell_edit, cell_delete and cell_move refuse a cell someone else changed since the agent last read it, so an agent can't overwrite text it never saw.
  • Request cells. A Markdown cell a person writes starting @agent (or @claude for Claude Code) is a request. notebook_requests lists the open ones; cell_add with answers puts the answer below the request and marks it done, in one room edit.
  • Waking an idle agent. ganymede mcp watch prints a line for each new request, and the journal plugin runs it as a Claude Code monitor, so a request reaches the agent between turns. A spike, mcp watch --edits (off unless GANYMEDE_WATCH_EDITS is set), wakes it on any edit once edits settle.

The journal plugin

The plugin makes Claude Code keep its analysis as a notebook. Its hooks (hooks/journal.mjs) run at four points: SessionStart reports the server; UserPromptSubmit asks for cells others changed since the agent's read mark and hands them over with the person's message; PostToolUse follows the agent's notebook tools, passes on the changes an @@changed line points to (so the agent sees a person's edit mid-turn), and records marked Bash steps as recorded cells; Stop checks the journal re-runs cleanly before the agent stops. Its monitor (monitors/monitors.json) runs ganymede mcp watch once the journal skill is in use.

FlowAn agent editing the notebook a person has open

  1. The person has journal/2026-11-13-x.ipynb open in the Mac app, so its room exists and the app is synced to it.
  2. Claude Code calls cell_run through ganymede mcp, which forwards it to the app's server at /mcp. With MCP turned on in the app's settings (AppMCP.swift), the app writes the server info file that ganymede mcp looks for, holding an mcp_token that opens only /mcp. The setting can also limit agents to reading, or to editing without running.
  3. mcp.rs adds a code cell to the room with agent metadata, then runs it through the room's execute queue (chapter 6). The new cell and its outputs reach the person's view as they arrive.
  4. The person edits a cell. The room broadcasts the update and credits it to the person, by the name the app sent in its awareness.
  5. The agent's next tool reply ends with an @@changed line naming the person. The plugin's PostToolUse hook calls notebook_read(since=<mark>), marks.rs diffs the notebook against the mark, and the agent gets the change mid-turn. Had it tried cell_edit on that cell first, the edit would have been refused.
  6. When the agent is idle, the person writes an @claude cell instead. mcp watch reports it through the plugin's monitor, and the agent answers with cell_add(answers=<id>).

The agent's edits reach the person at once through the room. The person's edits reach the agent on the dashed path: as an @@changed pointer on its next tool reply while it works, or through mcp watch when a request arrives while it is idle.

The design and the choices behind it are in docs/live-agent-edits.md (tracking issue #763). Still open there: whether waking on any edit stays (the spike, decided in #795), an "Ask the agent" button, and an agent cursor in the notebook.

cdp-kernel: the TypeScript kernel

cdp-kernel is a Jupyter kernel for TypeScript and JavaScript, about 14,000 lines of TypeScript. It started as an extraction of Deno's own Jupyter kernel, which is two halves joined by a handful of calls: the Jupyter protocol in plain JS, and a REPL isolate driven over the Chrome DevTools Protocol (CDP). cdp-kernel keeps that split and points the CDP half at other runtimes' --inspect endpoint. That is the name: the kernel drives a runtime over CDP. It is a separate process from the Rust core and knows nothing about Ganymede beyond the standard protocol, plus two optional extras (jupyter.host() and jupyter.params).

The cell pipeline

A cell is written as a TypeScript module, but CDP evaluates scripts. transform.ts closes the gap, as Deno's REPL does with swc:

  1. A type stripper (esbuild by default, sucrase as an option) removes types and compiles JSX, keeping a source map.
  2. acorn finds module syntax a script can't hold and rewrites it: import x from "m" becomes var x = await __cdpk.import("m"), and export is dropped, without moving lines.
  3. Node and Deno run the result with Runtime.evaluate in replMode, so top-level await and redeclared let work. Bun, workerd and celld have no replMode, so the cell runs inside an async function with its top-level names hoisted to globals.
  4. Imports resolve when __cdpk.import runs, differently per runtime: on Node, a resolve hook (runtime/node-hooks.mjs) re-parents imports to the notebook's folder and installs npm: and jsr: packages on first use; Deno uses its own resolution; workerd and celld can't load modules at runtime, so the kernel bundles a cell's imports with esbuild and sends the bundle with the cell.
  5. The last expression's value comes back as execute_result; the source map lets tracebacks and the debugger point at the cell's own lines.

Backends

Everything above the backend sees one ServiceManager. connect(config) in backends.ts builds it three ways:

  • ganymede: the stock ServiceManager over REST and websockets to a server. The normal case, including inside the apps.
  • ganymede with kernels: 'page': notebooks on the server, kernels in this page. For a server with no kernels of its own.
  • browser: everything in the page through JupyterLite's @jupyterlite/services, wired by hand in lite.ts. Notebooks in IndexedDB, kernels in Web Workers: cdp-kernel's browser build by default, with a fake websocket (mock-socket).

Which backend: ?token= or ?kernels= in the URL (how the apps launch it), then the saved connection, then the page's own server's login cookie, then the connect sheet.

Saving: two paths

Against a plain Jupyter server, NotebookSaver does what JupyterLab's document context does: one save at a time, last_modified checked before writing, autosave every 120 seconds, a check for outside changes every 5 seconds that locks the pane on conflict (or quietly pulls the new file when there are no local edits).

Against Ganymede, the pane joins the notebook's room instead (room.ts, chapter 6). The notebook model is built on the room's YNotebook, edits flow both ways live, and the server saves. The pane skips its disk checks and autosave entirely. This switch is why the apps and an agent can share a notebook.

FlowOpening a notebook (browser, Ganymede backend)

  1. App.tsx reads ?open=<path> (lib/launch.ts), connects the backend and shows the sidebar's folder.
  2. NotebookPane mounts for the path. On Ganymede, NotebookRoom.join calls PUT /api/collaboration/session/{path}, opens the room websocket and waits for first sync.
  3. JupyterLab's notebook widget renders the room's model. Output renderers come from jupyterlab.ts; HTML outputs go into sandboxed frames.
  4. SessionContext looks for a kernel already running for the file and rejoins it. If none, the toolbar says the kernel starts when you run a cell.
  5. The first run starts the kernel the file names (POST /api/sessions), and outputs arrive over the kernel websocket as in chapter 5.

packages/agent

An optional agent built on Pi Durable, off by default, turned on in Settings. settings.ts keeps provider, model and keys (keys in the Keychain in the apps); models.ts loads Anthropic, OpenAI, Google or a local OpenAI-compatible model on demand; index.ts and tools.ts drive notebooks through the Jupyter API. The panel that uses them is not built yet.

The Apple apps

The Mac, iPad and iPhone apps are one SwiftUI codebase in ganymede-ui's apple/ (about 19,000 lines of Swift, built with XcodeGen from project.yml). Each app runs the Rust server inside its own process through ganymede-ffi, loads the web app from it in a WKWebView, and draws its own native chrome around the notebook. The page shows only the notebook; Swift draws the sidebar, toolbar and menus. Priority 2, the apps as a full runtime, lives here.

The notebook page talks to the server exactly as a browser would. Swift sits between the hidden kernel web view and the server, carrying kernel messages through the ffi. On iPad and iPhone the kernel processes box is gone: only in-app and remote kernels remain.

In-app kernels

iOS won't let an app launch processes, and the Mac app wants a TypeScript kernel that needs no Node install. So the app runs cdp-kernel's browser build in one hidden web view (kernel.html, src/kernel-host.ts), one browser kernel per kernel the server starts. AppKernels.swift registers them through ganymede_kernel_register (chapter 9), so they show up in the server's kernel list and work with sessions, rooms and the execute endpoint like any other kernel. Messages travel server → Swift → kernel page, and back through the kernelHost message handler (src/lib/kernel-relay.ts has the diagram in its header). Because the kernel runs in its own web view, it survives a window reload, and only it gets the device bridge: no output rendered in the notebook page can reach native APIs.

The open question on the roadmap is replacing this web view kernel with a native in-app V8 engine, unless size or performance on device rules it out.

packages/device: the device API

packages/device (until 2026-11-13 the ganymede-device repo) gives cells a device global: await device.clipboard.readText(), haptics, dialogs, share sheet, file and photo pickers, Quick Look, and more. The TypeScript side (src/) is a preload installed in the cells' Worker; it sends calls over a comm or webkit.messageHandlers.device to the Swift DeviceBridge (swift/Sources), which checks a permission ledger and answers. Calls from a kernel on a remote server reach the app over a comm, answered by the page (src/lib/device-remote.ts). The contract is in packages/device/docs/protocol.md.

FlowThe Mac app opening a notebook

  1. You double-click report.ipynb in Finder. The app delegate records it; the first notebook window to see it takes it (WindowTarget.swift).
  2. AppModel already has the server running: ServerHost called ganymede_server_start at launch with JSON config (root /, static dir = the bundled web app, a token) and got back the URL.
  3. AppKernels has registered the in-app TypeScript kernel; kernelspecs on disk (Node, Python) are visible too.
  4. The window's WebView loads <url>?open=/Users/…/report.ipynb&kernels=server&chrome=native. The token in the URL becomes a login cookie, and the page drops it from the address bar.
  5. The web app (chapter 11) joins the notebook's room on the in-process server. The page posts PageState to Swift, which fills the native toolbar and window title.
  6. You press Run. The page starts the kernel over the server API. If it is the in-app kernel, the server's registered-kernel provisioner asks Swift to start it in the hidden web view; if it is a kernelspec, the server spawns a process and talks ZeroMQ, exactly as ganymede serve would.

Building, testing, shipping

The project's confidence comes from machine checks rather than people reading code: the e2e suites compare Ganymede against the real Jupyter stack, and every PR gets green CI plus an independent Claude review. Knowing which suite checks what tells you where a claim in this primer is enforced.

Build profiles

Cargo features choose what the server can do. ganymede-server defaults to zmq, subprocess, gateway and svg. The iOS slices of the XCFramework drop zmq and subprocess. The bottom crates (protocol, nbformat, documents, and kernel-host without its features) build for wasm; e2e/wasm-smoke/ proves it by running a notebook on the fake kernel under Node's WASI. Supported targets for the server are broad (Linux, macOS, Windows best effort, Intel and ARM); the apps target only macOS 26 and iOS 26 on ARM.

ganymede's CI has about 20 jobs, 13 of them required on main. A changes job (scripts/ci-changes.sh) skips jobs a PR can't affect, so a docs-only PR builds nothing. A weekly run tests against the latest upstream versions to catch drift. audit runs cargo deny for advisories and licenses.

In ganymede-ui, Vitest unit tests sit beside each source file and Playwright e2e tests run the built app against a real Ganymede and cdp-kernel; macos-app and ios-app build and test the Swift app on GitHub's macOS runners, and device and device-swift test packages/device. cdp-kernel's CI tests each runtime, the container image, the browser build and JupyterLab.

How a change lands

Every change is a GitHub issue, a PR that says Closes #N, green CI, and a dev-log entry in docs/notes/YYYY-MM-DD-<topic>.md. A scheduled reviewer session reviews each green PR and ends with Review: pass or Review: changes needed. Docs for features not yet released carry an **Unreleased.** note, which the release removes.

Releases

  1. cdp-kernel first, when it has changes: published to npm.
  2. Ganymede: scripts/release.sh opens a release/vX.Y.Z PR whose commit also moves the cdp-kernel pin and ganymede ui install's default. Merging tags it; release.yml builds binaries, the container image and the XCFramework.
  3. ganymede-ui: its release script moves GANYMEDE_REF and cdp-kernel to the latest releases, then builds the web app, the signed and notarized Mac app (with a Sparkle feed) and a TestFlight build.

Ganymede and ganymede-ui share their minor version; patches ship separately. Releases need the maintainer's explicit yes. A rolling main-build of the Mac app exists for trying main.

Open edges worth knowing about

These are the places where the code is moving, so a conversation about the project will likely land on them:

  • Native in-app engine. Replacing the hidden web view kernel with a native V8 engine in the apps (spikes/v8-engine in ganymede). Waiting on a device run and a decision.
  • Agents waking on any edit. Request cells, the edit check and mcp watch are built (chapter 8). Whether the agent should also wake on every settled edit is a spike waiting on a decision (#795).
  • Tailnet access. Tailnet identity in the server, sharing the Mac app's server on the tailnet, tokenless remotes and Tailscale SSH shipped in 0.12.0 but have not been tried on a real tailnet yet.
  • Several folders in one server. A design note (multi-root.md) recommends named mounts under one contents tree, each with its own rooms, for a sidebar of several folders on iPad and iPhone. Nothing is built yet.
  • Secrets in the apps. A ganymede-ui design note proposes device.secrets as shared named secrets with per-notebook access, waiting on answers.
  • Automation on iPad and iPhone. Shortcuts actions are Mac-only, since iOS suspends the in-app kernel shortly after the app goes to the background. ganymede://open links do work there.
